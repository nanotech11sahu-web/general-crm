# Decisions log

Format: decision, why, consequence. Newest last.

## Phase 0

1. **pnpm workspaces, packages export TypeScript source.** No per-package build step; apps run with `tsx` and tests with Vitest + SWC (decorator metadata). Simple for one maintainer. Production images will bundle with a build step added in Phase 7.
2. **Tenant isolation = two layers.** `TenantScopedRepository` (always merges `tenantId`) plus a Mongoose plugin (throws without tenant context, force-scopes every query/aggregate/save, blocks spoofed or mutated `tenantId`). Un-scoped `$lookup`/`$unionWith`/`$graphLookup` are rejected unless in pipeline form with a leading `tenantId` `$match`.
3. **System context is a closed list** (`SYSTEM_OPERATIONS`) reachable only through named functions in `createSystemOps`. Feature code cannot run arbitrary cross-tenant queries.
4. **Raw Mongoose is forbidden in `apps/*`**, enforced by an ESLint `no-restricted-imports` rule and an architecture test.
5. **Tenant-in-token for unauthenticated lookups.** Refresh and invitation tokens are `<tenantId>.<random>`; only the SHA-256 of the whole token is stored. This lets refresh/accept run inside a tenant scope with no system query. A forged prefix simply finds nothing.
6. **Refresh tokens rotate with reuse detection.** Replaying a rotated token revokes the whole family.
7. **Users and tenants are global collections** (no `tenantId`); membership links them. Login uses the named system ops `findUserByEmail` / `listMemberships`.
8. **Migrations:** `packages/db/src/migrations` with a small idempotent runner (changelog collection, migrate-mongo-compatible shape) so migrations run against a real replica set in tests. Spec named `migrate-mongo`; swap in its CLI later if preferred (the dependency is installed).
9. **Validators:** `$jsonSchema` on memberships, leads, integration_connections, integration_inbox.
10. **Secrets:** envelope encryption (fresh DEK per secret, AES-256-GCM, AAD = tenantId:connectionId, DEK wrapped by `KeyService`). `LocalKeyService` for dev/tests, `AwsKmsKeyService` for prod (untested against real KMS). Secret API is write-only; only a `••••1234` hint is stored for display.
11. **Webhook ingress** verifies signature before storing, dedupes on unique `(tenantId, connectionId, externalEventId)`, enqueues once, returns 200. Secrets are cached in-process for 60s to keep acks fast (a revoked connection is refused immediately; a *replaced* secret can take up to 60s to take effect).
12. **Outbox:** events written in the same transaction as the change; dispatcher leases events (`claimedUntil`), publishes, then marks dispatched. At-least-once; consumers must be idempotent.
13. **Lead model in Phase 0 is minimal** (needed for isolation/dedupe tests). Phase 1 extends it.
14. **Invitation delivery:** the invite token is returned to the inviter (copy link). Email sending arrives with the email connector.
15. **Not in Phase 0:** web app, Meilisearch wiring, MinIO usage, 2FA, rate limiting, Dockerfiles. Compose file includes the services.

## Phase 1

16. **Intake is one pipeline** (`LeadService.intake`): normalise -> validate (contacts + custom fields) -> dedupe via `lead_contact_index` -> create or attach "re-enquired" -> activity + outbox event. API, import (and later webhooks) all use it. Lost races on the unique contact index retry as a merge; concurrent submissions of one phone yield exactly one lead (tested with 12 parallel).
17. **Search without Atlas/Meilisearch (for now).** Name search = anchored prefix match on an indexed `nameTokens` array; phone search = denormalised `phoneNorms` (E.164, digits, last-10, suffix `s…`, prefix `p…` keys). Meets the spec's intent on plain MongoDB; swap in Atlas Search/Meilisearch behind `LeadSearch` when volume demands (no API change). Not yet load-tested at 500k leads.
18. **Custody.** `presentLead` is the only way lead data leaves the API: agents get masked contacts, never raw/normalised values or `phoneNorms`. Agents need >= 6 digits to phone-search (limits number-space probing). Export is manager/admin only, audited, and CSV-injection safe. Reduced-custody modes (tap-to-call) arrive with telephony in Phase 4.
19. **Visibility** (`own|team|all`) is applied in the query filter and re-checked on single-lead routes. Other-tenant ids return 404; same-tenant out-of-scope returns 403.
20. **Saved views and filters** go through a whitelist (`LeadQuery`); saved views reject unknown keys. Nothing user-supplied reaches Mongo as a raw filter.
21. **Merge** keeps all contacts/activities, soft-deletes the loser and stores a snapshot; undo is allowed for 30 days. Open tasks/cadences will be included when those exist (Phase 3).
22. **Offboarding**: deactivation + session revocation + audit + outbox event in ONE transaction; open-lead reassignment then runs in chunked short transactions (round-robin over a pool, or unassigned). Re-runnable. Live access tokens die immediately via a membership-status check (10 s cache, invalidated on offboard; other instances converge within the TTL).
23. **Import**: parsed rows are stored in `importrows` (not S3 yet; 20k rows / 5 MB cap). Rows carry an `outcome`, so re-runs and crash-resume are idempotent and final stats are recomputed from outcomes. Formula cells keep their value, never the formula. In Phase 1 the API runs the job in-process after returning; the worker has the same processor, and moving dispatch to BullMQ changes no behaviour.
24. **Not yet done in Phase 1:** web UI, Google Sheets import, AI-assisted mapping, object storage for uploads, virus-scan hook (stub point is `ImportService.create`).

## Phase 2

25. **Connections are manifest-driven.** Credentials are stored as one sealed JSON object per connection; the UI form comes from `credentialFields`/`configFields`. Platform-generated secrets (webhook signing secret) are revealed exactly once at creation; "reconnect" re-verifies the new credentials before swapping.
26. **One ingestion path.** Webhook -> verified + stored in `integration_inbox` (idempotent on `(tenant, connection, externalEventId)`) -> `InboxService.process` -> canonical events -> `LeadService.intake`. Non-retryable problems (unmappable payload, rejected lead) end `failed` and appear in **Needs attention** with replay; infrastructure errors throw so the queue backs off and retries, ending `dead` after max attempts.
27. **Verification can persist discoveries** (`VerifyResult.patch`): Meta page list/tokens/expiry, Google tab name. Credentials are re-sealed; non-secret config is merged.
28. **Meta webhooks are app-level.** One callback URL (`/hooks/meta-leadads`) for the whole app; routing is by page id to every live connection owning the page. Signature uses the platform's app secret; the GET handshake needs `META_WEBHOOK_VERIFY_TOKEN`. A valid signature always returns 200 (even for unknown pages) so Meta never disables the subscription. If `META_APP_ID/SECRET` are unset the provider is not registered at all (404).
29. **Provider enablement via platform env** (`createRegistry`): `META_*`, `GOOGLE_*`. Client credentials never go in env.
30. **Integrity layer** (`IntegrityService`): per-connection heartbeat = token expiry/refresh (refresh at T-10d, alerts T-7/T-3/T-1, expiry => revoked), provider health, webhook-subscription check with auto re-subscribe, learned silence detection, then the state machine `verified -> degraded -> failing -> revoked` (3 consecutive failed heartbeats => failing; a clean heartbeat recovers). Transitions write in-app admin notifications (deduped) with a reconnect link. Email/WhatsApp delivery plug into the `Notifier` interface in Phase 4.
31. **Silence detection** counts only 09:00-21:00 tenant-local time, needs a baseline of >= 10 events in 14 days, alerts after max(3x median gap, 2 business hours). Test events are excluded.
32. **Backfill reconcile** (hourly 2d / nightly 14d / weekly 80d) diffs provider leads against received inbox rows and stored leads, ingests only the gaps through the normal pipeline, and persists a `backfillCursor` for append-only sources (Sheets). Failed rows are never re-added (they already sit in Needs attention).
33. **Scheduling.** `planSweep` produces deterministic BullMQ job ids per time window, so two schedulers can't double-enqueue. The worker wires 5-min/hourly/nightly/weekly repeatable sweeps. **The BullMQ wiring itself (upsertJobScheduler, queues, workers) is untested against a real Redis**; the planning and processors are tested.
34. **OAuth.** State is single-use, tenant-prefixed (`<tenantId>.<nonce>`), stored server-side with a 10-minute TTL; Google uses PKCE. Tokens never reach the browser. Callback returns JSON, or redirects when `PUBLIC_APP_URL` is set.
35. **Outbound HTTP** from connectors goes through `createHttp`: https only, fixed host allow-list (so a hostile paging URL cannot reach internal addresses), timeouts, bounded retries and body size.
36. **Provider fixtures are *documented-shape* fixtures, not recordings from live accounts.** Graph API version defaults to v26.0 (`META_GRAPH_VERSION`). Meta App Review / Tech Provider status, real token behaviour, and Google consent-screen verification are still required before production. Meta/Google flows have not been exercised against the real services.

## Phase 3

37. **Forced discipline is server-side.** An outcome that requires a next action is rejected unless it carries a real future time (>= 30 s ahead, within a year) and a useful note (>= 10 chars, >= 2 words, not "call"/"follow up"). Outcome + task completion + next task + status change commit in one transaction, so a rejected sheet leaves nothing half-logged. A dialed/ended call with no outcome blocks further dialing and sits at the top of Today; skipping is capped per day (default 3, `settings.do.maxOutcomeSkipsPerDay`) and counted for Pulse.
38. **Tap-to-call is the only call mode so far** (Phase 4 adds provider calling). Durations are labelled `self_reported`. The `tel:` link necessarily carries the number to the phone (reduced custody, as the spec says); the Today queue and all lead payloads for agents never contain numbers.
39. **Today queue** is deterministic and explained: tiers = pending outcomes > new leads (priority = 100 + score + SLA boost + source weight) > overdue tasks (oldest first) > due within 30 min > stale. Each item has a reason string. Inbound-reply items arrive with conversations in Phase 4. Per-source weights and thresholds are tenant settings (`settings.do`, `settings.sla`).
40. **Missed/escalation** is a minute sweeper over open tasks (partial index): after the per-task grace (default 15 min) a task becomes `missed` (timeline entry + notifications to the agent and managers); after N hours (default 4) it escalates to managers, optionally returning the lead to the manager pool (`autoReassignOnEscalation`). All transitions are conditional updates, so overlapping sweepers are safe.
41. **Routing is opt-in.** Until a tenant defines rules (or a default pool) new leads stay in the manager pool. First matching rule wins (conditions: source, campaign, city, language, time of day in tenant timezone incl. windows that wrap midnight, score range, custom fields). Strategies: round-robin (atomic per-rule counter), least-loaded, specific user, sticky previous owner, team pool. Candidates must be active, not on leave, have required skills/language, be under `maxOpenLeads`, online and in working hours. If nobody is online/in hours the engine **relaxes** (still honouring skills/capacity) and says so in the explanation; if nobody is eligible the lead goes to the manager pool. Every decision is stored and written on the timeline. Rule payloads are whitelisted and may only reference members of the same workspace.
42. **SLA timers are lead state + a 30-second sweeper**, not delayed jobs: `sla.{state, claimDueAt, firstContactDueAt, reassignCount, triedUserIds}`. Durable across restarts, trivially cancellable (claiming or logging first contact), and idempotent (conditional update on state + due date). Precision is the sweep interval. After `maxReassignments` the lead goes to the manager pool with a notification. The spec mentions BullMQ delayed jobs; this gives the same behaviour with fewer moving parts (revisit if sub-30 s precision matters).
43. **Presence** lives in MongoDB for now (Redis was the spec's primary store): a heartbeat older than 5 minutes reads as offline. `on_call` is set only by the system (call start/end); clients may set online/away/offline.
44. **Not in Phase 3a/3b yet:** realtime push (SSE) and the PWA one-screen loop (3c), WhatsApp/SMS from the queue (Phase 4).

## Phase 3c

45. **Realtime = SSE over the normal bearer token** (`GET /v1/stream`). Events are derived from the transactional outbox and the notifications collection, so every API instance sees every event with no shared in-memory state. The hub polls (default 1 s, `REALTIME_POLL_MS`) only for tenants with a connected client; each event is routed per client by user/role (assignee only for `lead.assigned`/`task.created`/`task.due`, managers for missed/escalated/unclaimed, admins for connection alerts). Payloads carry ids and reasons, never contact details. `Last-Event-ID` replays up to 10 minutes / 200 events after a reconnect; at most 5 streams per user. A change stream would cut latency; polling was chosen for simplicity and testability.
46. **Auth for streaming from a browser:** `EventSource` cannot send an Authorization header, and tokens in URLs leak into logs, so the web client reads the SSE stream with `fetch` (streaming reader) and sends the header.
47. **Web app** (`apps/web`, Next.js App Router, plain CSS): login + the one-screen Today loop (call -> outcome sheet -> next action -> next lead), claim button, live updates with a 30 s polling safety net, presence heartbeat, PWA manifest + app-shell service worker (static assets cache-first; **API and stream are never cached**). The browser only talks to its own origin; Next proxies `/v1/*` to the API so the httpOnly refresh cookie stays same-site. **Deviation from the spec:** Tailwind/shadcn/TanStack Query are not used yet; this is the minimum screen that exercises the whole backend loop.
48. **Tap-to-call on the phone:** the app creates the call session, then hands the number to the dialer (`tel:`). Returning to the app (visibility change) ends the call and opens the outcome sheet automatically. The dialer hand-off goes through one overridable function so browser tests (no dialer) can stub it.
49. **Real-process verification.** The Nest testing module hides decorator-metadata problems, and `tsx` (esbuild) drops `emitDecoratorMetadata`, which silently breaks constructor injection. API/worker/ingress now start with `node -r @swc-node/register`; a boot test spawns the real API process against a real replica set, and the Playwright suite drives the production Next build against a real API process (mongodb-memory-server) in Chromium at phone size. The worker and ingress were also smoke-started (worker against a real `redis-server`: it boots and registers its repeatable schedulers; job *execution* through Redis is still unexercised).
50. **Not done:** inbound-reply queue items and WhatsApp/SMS buttons (Phase 4), lead detail/search/manager screens, i18n, accessibility audit beyond labels/roles, Lighthouse/performance budget measurement on a real mid-range phone.

## Phase 4 (messaging + telephony, through 4b)

51. **One send path.** `MessagingService.send` is the only way a WhatsApp/SMS message leaves the system (agent UI, cadences and automation all call it). It enforces: channel connected, lead consent (per phone + channel), WhatsApp 24 h session window (template required outside it), SMS requires an approved DLT template, mandatory `Idempotency-Key`, and the automated-send guards (quiet hours 21:00–09:00 in the tenant timezone, max 3 automated messages/lead/day).
52. **Idempotent sends with a retry lease.** The message row is written `queued` before the provider call; a retry with the same key reuses it (`sendingUntil` lease) so a crash between "queued" and "sent" can neither double-send nor strand the message. Statuses only move forward (queued→sent→delivered→read; failed is terminal).
53. **STOP/START are exact words** (case-insensitive, trimmed) so "please don't stop calling me" is not an opt-out. Opt-out is per phone+channel and blocks every automated and manual send.
54. **Fallback without a channel connection:** `wa.me` / `sms:` launch links, labelled self-reported in the response; no delivery tracking is claimed.
55. **Telephony has two modes with one flow.** *Cloud* (Exotel connection + the agent's number mapped in `agentNumbers`): the provider rings the agent first, then bridges the lead; the lead's number never reaches the browser; duration/outcome come from the provider callback (`durationSource: system`). *Tap* (no connection / unmapped agent): `tel:` dialer, self-reported duration. `POST /v1/calls` returns `mode` so the UI knows which to do. A failed provider call is marked `missed` immediately so the agent is never stuck behind an outcome sheet for a call that never happened.
56. **Call callbacks are untrusted input.** They use the per-connection token webhook path (constant-time compare), are stored raw, answered 200, and processed by the worker like every other event. Exotel posts `application/x-www-form-urlencoded`: signature/token is checked on raw bytes first, then the body is decoded to a map for storage; the event id is `CallSid:Status[:rec]` so redeliveries collapse to one inbox row, and `handleEvent` is itself idempotent (a second `ended` is a no-op).
57. **Recordings** are downloaded by the worker (host allow-list, https only, 25 MB cap), written to the `ObjectStore` under `tenants/{id}/recordings/…` and never referenced by key in any API response. Access = `GET /v1/calls/:id/recording` (needs `calls.listen`, i.e. managers/admins; audited as `recording.accessed`) → a 5-minute HMAC-signed URL → `GET /v1/recordings/:token` (public route; the token is the credential; tampered or expired = 404). Filesystem store for dev/single node, S3-compatible store for production (`S3_*` env).
58. **`call.ended` over SSE** goes only to the agent who made the call; the Today screen opens the outcome sheet with the system-verified duration. In cloud mode there is deliberately no "call finished" button — the provider callback is the truth, and the 30 s poll surfaces the pending outcome if the event is missed.
59. **Verification status:** Exotel, WhatsApp Cloud and MSG91 request/response shapes come from their public docs and are encoded as fixtures; **none has been exercised against a live account**. The browser e2e covers tap mode only (cloud mode needs an https provider host); cloud mode is covered by the API-level test with the provider fetch switched.
60. **Left for 4c:** cadences/first-touch automation, inbound replies as a Today tier, `message.in` over SSE, and WhatsApp/SMS buttons + thread view in the web UI.

## Phase 4c (cadences, first-touch, replies in the queue, thread UI)

61. **Enrollment state lives in MongoDB, not delayed jobs.** An enrollment materialises its steps with absolute `runAt` times; a 30 s sweeper (`cadence.sweep`, same pattern as SLA/tasks) runs whatever is due, per tenant, under that tenant's context. Durable across restarts, trivially stoppable, and editing a cadence never rewrites in-flight enrollments.
62. **Stop conditions are checked twice.** Eagerly (inbound reply, STOP, connected call, human status change call `stopFor` the moment they happen) *and* again at run time before every step (reply since enrollment, connected call, status change, lead closed/deleted, first-touch only: a human already contacted the lead). A missed eager call can therefore never produce an unwanted send. Per-cadence `stopOn` flags can switch individual conditions off.
63. **Every automated message goes through `MessagingService.send`** with idempotency key `enr:{enrollmentId}:{step}`: consent, DLT/template rules, quiet hours (21:00–09:00 tenant time) and the 3-per-lead-per-day cap all apply. Quiet hours *defer* the step to when the window ends; the cap defers it by an hour; an ineligible/rejected message is recorded as `skipped:<code>` and never retried; transport errors retry the same key up to 5 times with growing delay, so a retry cannot double-send. STOP stops the whole enrollment.
64. **First touch** is a tenant setting (`settings.firstTouch`: channel, approved template, delay). Only brand-new leads enrol (never re-enquiries/merges), and leads that came from a manual entry, import, API or from the lead messaging us first get no automated opener. A human contacting the lead first cancels it.
65. **Cadences** have 1–10 time-ordered steps (message from an existing template, or a task for the lead's owner with a concrete note, same quality bar as agent next actions). They start manually (`POST /v1/leads/:id/cadences`) or automatically via `enrollOn` (status ids / outcome ids). Definitions and first-touch settings need `rules.manage`; agents can enrol/stop on leads they can see.
66. **Inbound replies are a Today tier** (after tasks, before stale), one item per lead per owner, longest-waiting first, showing channel, age and a preview. Opening the thread marks it read, which clears the item. `message.in` over SSE goes only to the lead's owner and carries no contact details.
67. **Thread UI** (`/lead/[id]`): channel tabs for connected channels only; WhatsApp free text inside the 24 h window, templates outside it; SMS templates only; per-attempt idempotency key kept across retries; with no channel connected it offers the self-reported `wa.me`/`sms:` launch.
68. **Test caveats:** the browser e2e plants an inbound SMS through a test-only seeding endpoint in `apps/api/scripts/e2e-backend.ts` (providers are unreachable from a browser test), so it covers queue → thread → read, not an actual send. Cadence execution is covered with real replica-set tests and a fake provider; the BullMQ scheduling of the 30 s sweep itself has only been boot-tested.
69. **Playwright now builds the web app itself** (`next build && next start`, with `API_URL` baked in): a stale build once made every test fail with a misleading "could not sign in".

## Phase 5 (Pulse)

70. **Live aggregation now, daily rollups for history.** KPIs, team board, leakage, sources and scorecards are computed on demand from the operational collections (all tenant-scoped, indexed on `tenantId` + time; row caps of 50 000 per query). The spec's `$merge` rollups exist as one `pulse_daily` document per tenant per local day (KPIs, counts, leakage) written when the digest runs; they feed `/pulse/trend` and the digest. Rollups per user/source and secondary reads are the scale-up path when a tenant outgrows live queries — not built yet.
71. **Metric definitions (also the tooltips' source of truth).** *Response time* = first contact − (assigned, else created) for leads created in the period; median, plus % within SLA where a lead counts once contacted or once its deadline passed (stored SLA timer, else tenant default). *Connect rate* = connected outcomes ÷ calls with a logged outcome. *Avg talk time* = mean duration of connected calls with a duration. *Conversion* = won ÷ leads created in the period (cohort, not "wins this week"). *Follow-up completion* = tasks done within grace of their due time ÷ tasks that fell due (cancelled excluded). *Qualified* (sources) = reached the 3rd open stage or won, so it works across presets. Trend = vs the previous equal period ("today" compares with yesterday up to the same time of day); no trend is shown when the previous value is empty.
72. **Self-reported calls are never hidden.** Every call-based number ships with `verifiedCallShare`; the UI marks agents whose figures include self-reported durations, and an insight nudges tenants without cloud telephony.
73. **Leakage returns lead ids** (≤ 200 per bucket) so the existing bulk-assign endpoint is the "one-click reassign"; Pulse itself never mutates leads and never returns phone numbers.
74. **Insights are rules first**: untouched leads, missed follow-ups, response time ≥ 1.5× the previous week, < 70 % within SLA, mostly self-reported calls, ≥ 5 skipped outcome sheets, and a source whose conversion fell > 30 % week on week (min. 10 leads each side). AI wording is a Phase 6 option and only rephrases these.
75. **Digest**: hourly sweeper; once a tenant's local digest hour (default 08:00) has passed it rolls up yesterday and creates one in-app `pulse.digest` notification for managers+ (deduped per local day, so reruns and overlapping workers are harmless). **Email and WhatsApp digest delivery are not built** (no email connector yet; WhatsApp needs a per-manager opted-in number) — the payload already carries the text.
76. **Access**: `pulse.view` (managers, admins, owners) is tenant-wide. **Known gap:** managers' *lead* visibility is team-scoped while Pulse is not, so a manager can see a leaking lead they cannot reassign through bulk until teams are configured; scoping Pulse by team is a follow-up. Settings (goal, digest hour, thresholds, gamification) need `tenant.manage`; exports are admin/owner only, audited and formula-injection-safe. Agents get their own goal ring + streak and the follow-up leaderboard (names and percentages only); switchable off per tenant.

## Phase 6 (AI, optional)

77. **AI is a connector like any other.** `ai-groq` implements `complete` / `listModels` behind the connector contract (OpenAI-compatible endpoint, https + host allow-list, no automatic retries so a 429 reaches the AI service). Each tenant brings its own key (stored encrypted, write-only); the platform holds **no** Groq key, so the spec's "dev key in env" shortcut is deliberately not implemented (tests use a fake provider). Request shapes (chat completions, `response_format: json_object`, `max_completion_tokens`, `reasoning_effort` for gpt-oss) follow Groq's public docs; **not exercised against a live key**. Review Groq's commercial-use and data-retention terms before sending real customer data.
78. **Everything goes through one call path** (`AiService.call`): feature on? kill switch? daily cap? → configured model present in the key's model list (cached 10 min) → provider call → JSON parse → zod schema → one retry on invalid output → usage + audit row. A failure surfaces a friendly error and never a provider message; the lead/app flow never depends on it. Model tier is per feature (fast: mapping, search, autofill, scoring, next action; smart: summary, assessment), `max_completion_tokens` has headroom and fast tasks use low reasoning effort.
79. **AI never writes lead data directly.** Output becomes an `ai_suggestions` row (type, payload, confidence, model, prompt version, input hash). `accept` is the only writer; it re-validates (custom-field values against the tenant's definitions — unknown keys dropped, select values normalised, **existing values never overwritten**; next actions through the same quality rules humans face). Levels: 0 off, 1 suggest (default), 2 auto-apply **only** for summary / autofill / scoring / assessment (lead metadata; never contacts a lead, never creates work for a person). Level 3 (autopilot) is not built. A newer suggestion supersedes a pending one; identical masked input is served from the stored suggestion (no request, no quota).
80. **Privacy and injection.** Phones and e-mails are masked before text leaves the platform; only a minimal context is sent (name, city, status, source, fields, form answers, last 15 activities, each clipped). Lead-derived text is wrapped in `<lead_data>` and the system prompt says it is untrusted data; the model can only answer with a schema-validated JSON object, has no tools, and no code path executes model output. Natural-language search returns a **filter object with a closed key set** (`.strict()`), compiled server-side with escaped regexes and ANDed with the caller's visibility scope — never a database query.
81. **Controls.** `settings.ai`: `enabled` (default false; refuses to turn on without a verified AI connection), `killSwitch`, `dailyCap` (requests per tenant-local day, default 200, "AI limit reached, resumes tomorrow"), per-feature level. Usage per day/feature (requests, failures, tokens) is visible to managers. Every call and every applied suggestion is audited.
82. **Examine every new lead (12b stage 1), asynchronously.** A 60 s worker sweep sends **one consolidated call per lead** (validity, summary, score + reasons, extracted fields, best first action, missing info) for tenants with AI on, only for leads from the last 24 h, once each, stopping quietly at the cap or on a 429. Intake never waits for it. Accepting applies score/summary/fields/next-best-action together (score feeds the existing queue ordering, and the Today card shows e.g. "Hot: asked for price…"); suspect/junk leads get an `ai:suspect` / `ai:junk` tag for review rather than being hidden.
83. **Built: features 1–6 plus the assessment** (smart import mapping, summary, auto-fill, outcome + next action, scoring, NL search) with API, worker sweep, lead-page AI panel and an admin AI settings page. **Not built:** inbound message intelligence, reply/template drafting, duplicate intelligence, stale-lead revival, AI manager-insight wording, transcription/call QA, knowledge base, autopilot/qualification conversations, per-tenant scoring weights. Browser e2e covers the off-by-default and permission behaviour only; the suggestion flow is covered by real-DB domain and API tests with a fake provider.

## Phase 7 (hardening) — 7a to 7d

84. **HTTP defaults are safe, shared by API and ingress** (`packages/platform/src/http`): safe request ids (client ids accepted only if they cannot inject into logs/headers), structured JSON logs that never include bodies/headers/cookies, security headers + `Cache-Control: no-store` on API responses, CORS closed unless `CORS_ORIGINS` lists an origin, CSRF origin check for requests that carry the refresh cookie without a bearer token (SameSite=Strict stays the first line), explicit input length caps (passwords ≤128 before hashing), and **boot refuses unsafe production config** (weak/placeholder secrets, missing KEK, non-https app URL, `RATE_LIMITS=off`, no Redis).
85. **Rate limits are layered and fail open.** Anonymous auth routes: per-IP buckets (login 10/min, signup 5/h, accept 10/min, refresh 60/min); authenticated traffic per user (600/min) and per tenant (3 000/min); counters in Redis (shared across instances) or memory; a Redis outage logs and lets traffic through rather than locking everyone out. Failed sign-ins lock an account+IP after 5 and an account after 25 failures in 15 min, uniformly for unknown accounts (no existence leak). Webhook ingress never throttles by IP (Meta/WhatsApp share one callback URL): it caps each *connection* (6 000/min) and cuts off an IP only after 60 *rejected* requests/min.
86. **TOTP 2FA** (RFC 6238, implemented in-house and tested against RFC 4226 vectors): secret sealed with the key service, each time step usable once, 10 hashed single-use recovery codes, login returns `totp_required`/`totp_invalid`. Sessions: logout-all and password change revoke every refresh family; disabled users and suspended/deleting workspaces can no longer refresh or call the API (membership cache also checks tenant status). Not built: enforced 2FA per role, WebAuthn, email-based reset flow (needs the email connector).
87. **Observability:** `/healthz` (process), `/readyz` (Mongo + Redis), token-gated `/metrics` (HTTP counters/latency histogram by route *template*, pipeline gauges: pending/dead webhooks and their age, outbox backlog, late SLA timers, connections by status; worker adds queue depth/DLQ and per-job last-success/duration). Per-workspace `GET /v1/ops/health` + admin Health page use the same numbers as the alert rules (ingest lag, DLQ, send failure rate, SLA/task timers late, outbox lag, unhealthy connections); the 5-minute worker sweep nudges admins once per rule per hour. `deploy/prometheus/alerts.yml` carries the platform alerts. Error tracking (Sentry) is not wired: needs a DSN and an account decision.
88. **Data lifecycle (DPDP/GDPR):** per-lead export and hard erasure (activities, threads, calls + recording files, merge snapshots, raw webhook copies, notifications), leaving only a per-tenant salted phone hash so the platform never messages that number again, and a PII-free audit row. Workspace export is NDJSON (extended JSON, typed ids/dates) **without credentials, password hashes, token hashes or sessions**; the restore path loads it into a fresh database and the tests compare counts. Retention (nightly): recordings after N days (default 180), soft-deleted leads after N days (default 30). Workspace deletion: owner + password, 14-day grace, cancellable, then every document, recording prefix and single-workspace users are purged. Import rows keep the uploaded file's contents until the import job is deleted: not yet covered by retention.
89. **Backups:** `scripts/backup.sh` (mongodump archive + checksum + retention + optional S3), `scripts/restore-drill.sh` (restore into a scratch DB, verify, drop) and `verifyDatabase()` (migrations applied, every declared index present, no tenant-owned document without tenantId; unit-tested). **The shell scripts have not been executed here (no mongo tools in the build sandbox); run one real drill before launch.** On Atlas, use continuous backup + PITR as the primary and these as an independent second copy.
90. **Performance is a test, not a claim.** `perf.test.ts` seeds 60k leads (3 tenants) and audits 26 hot queries with `explain` (no COLLSCAN, no large in-memory sort, bounded docs examined). It found five real problems, now fixed by additive migration `20250601000001-indexes-v2` (newest-first lists, agent-scoped lists, unread-reply queue, Pulse/health windows). API p95 at that scale: list/search/queue < 300 ms, detail < 400 ms, Pulse < 2 s; command counts do not grow with rows (no N+1). Webhook ingress: ack p95 ≈ 30 ms at steady load; a 1 000-event burst runs at ≈ 12 k/min on one process, exactly-once under redelivery. Today renders in ≈ 0.8 s on an emulated mid-range phone (4× CPU, 150 ms RTT) after parallelising its first requests. k6 scripts for staging runs are in `load/`. From here on, **new indexes go in an `INDEXES_V2`-style additive migration, never into the init migration.**

Dependencies: postcss/uuid pinned via pnpm overrides and csv-parse upgraded; CI now audits (`--audit-level=high`), runs CodeQL and Dependabot.

## Phase 8 (sell: plans, billing, landing, demo data, support tooling)

95. **Plans live in code** (`trial/starter/growth/scale`, `PLANS_JSON` override). **Prices and limits are placeholders** the business must set before launch. Limits: seats, connections, AI on/off, cloud telephony, and a *soft* monthly lead figure that is displayed but **never blocks lead intake**.
96. **Trial and status.** Every workspace gets a lazy 14-day trial (`ensureTrial`). Subscription status is rolled lazily on read (`trialing → expired`, `active → past_due → grace → expired`), so no cron is required for correctness; a worker sweep retries failed billing events and sends hourly reminders.
97. **Read-only, not locked out.** When a workspace is expired or past grace, a global guard returns 402 `subscription_required` for writes; reading, export, privacy and account-security routes (`@AllowRestricted()`) keep working so customers can always get their data out. Automation and AI spend pause while restricted.
98. **Seats** = active members + open invitations; inviting beyond the plan seat count is refused; seat changes via the provider apply at cycle end.
99. **Razorpay** is the first provider behind a `PaymentProvider` port: hosted checkout link, cancel at cycle end, HMAC-SHA256 webhook at `POST /hooks/billing/razorpay` on the ingress, idempotent `BillingEvent` log. **Fixture-tested from public docs, not verified live.** Manual/invoiced customers are supported by the operator `subscription` endpoint.
100. **Sample data** (tag `demo`, fictional 99999 000xx numbers, 24 leads, tasks, self-reported calls) loads/removes in one click; demo leads are blocked from messaging, calls and first-touch automation, so they can never contact a real person. Erasure of demo leads skips suppression.
101. **Operator tooling** (`/platform/*`): disabled (404) unless `PLATFORM_ADMIN_TOKEN` ≥ 32 chars; constant-time bearer check; optional `PLATFORM_ADMIN_IPS`. Shows plans, counts, health and alerts only — no customer content, no impersonation. Suspend/unsuspend, extend trial and set a manual plan; every action is written to `PlatformAudit`. A customer JWT is not an operator credential.
102. **Landing page** (`/`) is static with live pricing from `GET /v1/plans` and redirects signed-in users to Today; Billing page and trial/read-only banners reflect server entitlements.
103. **Still open:** invoices/GST documents, proration, dunning emails (needs email connector), usage-based billing, a web UI for the operator API.

## Phase 9 (completing the open items)

### 9a Admin screens
104. **One Admin console** (`/admin`, tabs: Pipeline, Routing & SLA, Templates, Automation, Import, Team, Views) over the same permission-checked API; nothing new is reachable by a role that could not already call the endpoint. Missing API pieces added: status rename/recolour/required-fields and a whole-pipeline reorder (must list every status once), lost-reason and custom-field edits (key and type are immutable because stored values depend on them), custom-field delete (values on leads are kept), and Teams CRUD. Statuses are never deleted (leads reference them).
105. **A lead list exists now** (`/leads`): search, status/owner/untouched filters, saved views (managers can share), bulk status/tag/assign/delete, CSV export for managers. Agents keep masked contacts and no export.
106. **Operator console** (`/operator`) is a thin client over `/platform/*`: the token is typed in and kept in memory only. The web app proxies `/platform` only when `OPERATOR_CONSOLE=on`; prefer a separate, IP-restricted deployment (behind a proxy the API's IP allow-list sees the proxy address unless `TRUST_PROXY` is set correctly).

### 9b Email
107. **Transactional email only.** One `Mailer` port: SMTP (any relay) via `SMTP_URL` + `MAIL_FROM`, a null mailer when unset (flows degrade to "copy the link"; production boot logs a warning), a memory mailer for tests, and a file-capture mailer that only works with `NODE_ENV=test` for browser tests. **Not built:** a per-customer email *channel* for messaging leads (it needs per-tenant SMTP/IMAP or inbound parsing, SPF/DKIM guidance and unsubscribe handling).
108. **Password reset:** `POST /v1/auth/forgot` answers identically for known and unknown addresses (mail is sent in the background so timing does not leak either), ≤ 3 links per user per hour plus a per-IP bucket, 60-minute single-use links stored only as hashes (global `passwordresets`, TTL cleanup), reset signs out every session and emails a "password changed" notice. Changing the password also emails a notice.
109. **Invitations** are emailed and the link is still returned to the admin (an outage never blocks inviting).
110. **Notices by email** come from a worker sweep over `notifications` (not from the code that raised them): whitelisted kinds only (billing trial/expiry/payment, connection failing/revoked, daily digest), recipients derived from the audience, per-member opt-out for connection alerts and the digest (**billing notices to owners/admins cannot be switched off**), per-recipient `emailedTo` so a retry after a partial failure never duplicates, 24-hour retry window, opted-out notices marked handled. Migration `20250801000001-email` adds the reset collection and a recent-notifications index.
